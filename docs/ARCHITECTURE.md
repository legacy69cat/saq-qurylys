# Предлагаемая архитектура

Статус на 18 октября 2026: реализованы реестр, ручной ввод, Gateway-адаптер, проверка гипотез, ручная проверка основания, сигналы и журнал. Живая оценка модели ожидает настройки ключа. Единое TypeScript-приложение React/Next.js использует локальную SQLite и серверный AI SDK 7. Облачного деплоя нет.

## Разделение ответственности

1. `domain/risk`: чистая функция расчёта по подтверждённым факторам и версия правил.
2. `domain/analysis`: валидация данных и цитат; переходы статусов — `server/db/workflow`.
3. `server/db`: сохранение объектов, публикаций, факторов, сигналов и событий.
4. `server/ai`: вызов модели, проверка структурированного ответа и цитат; ключ только на сервере.
5. `app` и `components`: реестр, карточка ЖК, реклама, проверка гипотез, сигналы и печать.

Зависимости и их версии зафиксированы в package-lock.json. SQLite подключена через node:sqlite; используется Node.js 24.15+ ветки 24.x. Миграции версионируются в schema_migrations и применяются транзакционно. База создаётся только явной CLI-командой, GET-маршруты и страницы читают её, Server Actions выполняют транзакционную запись. Анализ выполняется через Vercel AI Gateway; модель задаётся переменной AI_GATEWAY_MODEL, ключ — AI_GATEWAY_API_KEY.

Production использует Turso через @libsql/client; локально используется SQLite. Общая асинхронная обёртка Database поддерживает транзакции. В Vercel локальная файловая БД запрещена.

## Данные

| Сущность | Основные поля |
|---|---|
| Project | id, название, адрес, координаты?, developerId, стадия, isDemo |
| Developer | id, название, БИН при наличии источника |
| LegalBasisCheck | projectId, тип основания, статус unknown/present/absent, источник, дата фиксации, проверивший, время проверки |
| Evidence | id, тип, URL?, сохранённый текст/локальный файл, publishedAt?, capturedAt, isDemo |
| Publication | id, площадка/аккаунт, дата, evidenceId, projectId?, статус привязки |
| AIAnalysis | publicationId, модель/версия промпта, статус, структурированный результат, ошибка?, createdAt |
| Factor | projectId, R1–R6, proposed/confirmed/rejected/unknown, evidenceIds, автор и время проверки |
| ProgressObservation | projectId, claimed/verified, процент, evidenceId, observedAt |
| Signal | projectId, версия, снимок балла/факторов/доказательств, статус, автор, createdAt |
| ReviewEvent | entityId, действие, прежний/новый статус, комментарий, actorId, createdAt |

Для R5 хранить обе оценки готовности с независимыми источниками и датами. Для R6 хранить подтверждение и комментарий аналитика: конкретный порог «существенности» ТЗ не задаёт. Все существенные сведения должны иметь происхождение. Метки времени хранить в UTC, отображать в Asia/Almaty.

## ИИ-сценарий

Ввод: новый текст рекламы и название явно выбранного человеком ЖК. Вывод: summary и до двух suggestions с полями code (R2/R3), quote (дословная цитата), explanation и confidence. Есть подсказки совпадения названия ЖК; привязка подтверждается человеком. OCR скриншотов вынесен в общий recognizeAdPhoto для сайта и Telegram. Уверенность модели не считать откалиброванной вероятностью.

Сервер проверяет схему ответа и совпадение цитаты с исходным текстом. Содержимое рекламы обрабатывается как данные, а не инструкции модели. Неуверенный результат маркируется. Аналитик подтверждает привязку и фактор либо отклоняет гипотезу. Только затем меняется скоринг.

При тайм-ауте, невалидном ответе или недоступном ключе сохранённая публикация остаётся доступной; можно повторить анализ или проверить вручную. Кэш и ранее сохранённые анализы должны явно отличаться от нового вызова.

## Состояния и согласованность

- Гипотеза: `proposed → confirmed/rejected`. Решение окончательно для этой гипотезы. Подтверждение добавляет её доказательство в фактор R2/R3; отклонение не отменяет другие подтверждения. Изменение основания обновляет R1 и журнал.
- Сигнал создаётся сразу в `pending`, затем переходит в `confirmed` или `returned`.
- Возврат требует комментария. Повторная подача создаёт новую версию для рассмотрения.
- Подтверждение требует автора, времени и доступных доказательств; запрещается автоматическое подтверждение ИИ.
- Подтверждённая версия сигнала хранит снимок данных. Новые факторы меняют текущий риск ЖК, но не переписывают ранее выгруженный сигнал; интерфейс показывает, что появилась новая информация.
- Изменение фактора и событие журнала выполняются в одной транзакции; риск вычисляется заново при чтении. Повторное нажатие не создаёт дубли решений.

## Границы MVP

Локальное однопользовательское демо: автор действия вводится вручную; аутентификации нет. Для публичного демо потребуется ограничить запись или изолировать пользовательские сессии. Реальные государственные API не подключаются. Печатная HTML-страница с сохранением PDF через браузер закрывает требование выгрузки без отдельного PDF-сервиса.

Секреты исключить из Git; текст рекламы выводить безопасно; ограничить размер ввода; не загружать произвольные URL сервером. Внешние ссылки хранить как источник, а не как команду на импорт. SQLite требует постоянного диска — возможность деплоя проверяется отдельно.

## Реализация хранения

Миграция 2 добавляет analysis_runs, suggestions, signals и audit_events. Гипотезы отделены от подтверждённых факторов: proposed учитываются только как необходимость проверки. AI-запрос выполняется вне транзакции; запуск фиксируется до запроса, результат записывается атомарно. Уникальный индекс допускает один running-анализ на публикацию; зависший запуск можно повторить через 2 минуты.

Сигнал хранит JSON-снимок Project и SHA-256 отпечаток. Статус и решение хранятся отдельно. Подтверждение проверяет актуальность снимка в транзакции. Уникальный индекс допускает один pending-сигнал на ЖК; новая подача после возврата получает следующую версию. Журнал содержит projectId, автора, действие, детали и время.

## Сбор публичных публикаций

Миграция 3: `social_searches` → `collection_jobs` → `collection_matches` → `collected_posts`; `collector_state` хранит heartbeat. UI `/monitoring` пишет задания через Server Actions. Отдельный Node-процесс `scripts/collect-social.ts` каждые 15 секунд планирует запросы, атомарно резервирует бюджет, запускает Apify и читает завершённые наборы. Платный POST не повторяется при тайм-ауте, падении между запросом и записью run ID или ответе 5xx. Просроченный `starting` становится `uncertain`; GET можно повторять. Импорт и завершение задания — одна SQLite-транзакция. Частичные результаты неуспешного удалённого запуска сохраняются с явным статусом ошибки.

Клиент Apify использует фиксированный API-хост и серверный Authorization header. Пользовательские URL не загружаются. Сохраняются только поля публикации, без исходного JSON/комментариев/видео. Ни одна собранная запись не попадает в factors/evidence автоматически. Существующие сценарии демо-ЖК остаются отдельными.

Пакеты поиска определены в `domain/search-packs.ts`. Ключевые фразы хранятся с разделителем `|` в неизменяемой настройке поиска; адаптер строит массив запросов TikTok/Facebook и строку запросов Instagram, ограничивая число результатов на каждую фразу. Это пакетный поиск слов, не отдельный API сбора по хэштегам. `installSearchPacks` выполняет идемпотентную установку выбранных групп транзакционно.
